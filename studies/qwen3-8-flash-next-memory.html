Memory: Qwen3.8-Flash-Next
on 16 GB300s

A 125B-A6B decoder with a 51-billion-parameter lookup table. The table is free to compute and expensive to keep. The question is which GPU keeps it, and what else is live there at the same time.

176.94Btrainable text-decoder parameters
16GB300 GPUs, one NVLink domain
288 GiBHBM3e per GPU (eight 36-GiB stacks)
2.13 TiBlogical FP32 update state

Anchor recipe: PP2 with interleaved 1F1B and two virtual stages per rank, DP-shard8 / EP8 / TP1 / CP1, 16 microbatches of 16,384 packed tokens per DP rank (documents split at 4K), full layer recompute, Dist-MoE with an activation-slot capacity factor of 0.5, DistMuon plus AdamW plus Adam for the PLE table, FP32 master weights and gradient reduction, BF16 compute. No vision encoder, no MTP head. Every number on this page is derived from shapes, dtypes and schedules; none is measured.

First, name the copies

FP32 history, BF16 compute, and one table without a BF16 view

The FSDP storage shard is the master weight: the optimizer updates it in FP32, and FSDP casts a BF16 compute view for forward and backward. There is no second, full-model BF16 master. The PLE n-gram table is the exception that shapes this whole study: FSDP ignores it, so it never gets a BF16 view. Each data-parallel rank owns a contiguous range of rows in FP32 and only the rows a microbatch looks up are cast to BF16.

The unavoidable bill

A 2.13-TiB bill, and a third of it is one table

The architecture study audited 179,999,981,424 checkpoint elements. Remove the 448,931,056 vision-encoder and 2,607,150,848 MTP parameters and 176,943,899,520 trainable parameters remain. The recipe's first-match optimizer patterns split them three ways:

Ideal 16-way average = 136.15 GiB / GPU

The table is free to compute: a token reads 16 rows of 160 values, 5 KiB in BF16. But every one of its 51.2 billion parameters needs a master, a gradient and two moments, because Adam is applied to the whole table. Sparse access reduces arithmetic, not optimizer state. The same is true of the routed experts: choosing 10 of 512 per token does not shrink their 120.8 billion stored weights.

The average hides the hard part. 136 GiB per GPU would fit easily on a 288-GiB device. But no GPU holds the average: PP gives each rank half the decoder, EP gives each rank 64 experts, and the table lives entirely on the stage that runs layer 2. This tally also excludes BF16 views, unsharded gradients, activations and workspaces.
Who holds what

PP, EP, FSDP and row owners divide different things

PP2 × VPP2

Four chunks of 12 layers

Chunk 0 holds the embedding and layers 1–12, including the PLE layer. Chunk 3 holds layers 37–48, the final mixer and the LM head. PP rank 0 runs chunks 0 and 2; rank 1 runs chunks 1 and 3.

EP8

64 experts per layer per GPU

512 / 8 = 64. With 8 DP ranks per stage, expert FSDP is 8 / 8 = 1: EP alone divides the expert bank. Each GPU stores 24 layers × 64 experts of its stage.

FSDP8

Dense weights over 8 ranks

Attention, GDN, shared experts, routers, mixers, embedding and head are sharded over the 8 DP ranks of their stage. They are 2.8% of the parameters, so FSDP barely matters for the state bill here.

Row owners

The table lives on PP rank 0

The 320,001,536 rows are split over the 8 DP ranks that run layer 2: 40,000,192 rows, or 6.4 billion parameters, per GPU. At 16 bytes per parameter that is 95.37 GiB per rank-0 GPU, and nothing on rank 1. 

On PP rank r with dense parameters D_r, routed parameters X_r and table rows P_r:
Resident parameters / GPU = D_r / 8 + X_r / EP + P_r * 160 / 8
FP32 state / GPU          = 16 * (Adam + AdamW part) + 12 * (Muon part)
BF16 views / GPU          = 2 * (D_r + X_r / EP)        # the table has no view

Rank 0 carries 95 GiB more persistent state than rank 1, and the table accounts for all of it. The experts are symmetric: each rank holds 24 layers of 64 experts, 28.1 GiB of master and the same of momentum. The pipeline balances layers, not bytes.

A 5 KiB lookup behind a 95 GiB parameter. A microbatch of 16,384 tokens asks for 262,144 table rows. Each hash head reads only its own row range, so an owner receives at most min(T, overlap) distinct IDs per head from one peer. An owner's 40M rows span two full heads and the edge of a third: at most 33,180 IDs per peer, a capacity fixed by the table layout, not the data. All 8 owners' replies fit in 81 MiB of BF16 rows. The table never moves; only IDs and rows do.

Follow the bytes through one layer

What a layer saves, and what it only borrows

With full layer recompute, a layer keeps only its four-stream input until backward. Everything else is regenerated one layer at a time, with two deliberate exceptions: the Dist-MoE call keeps what its slot allows, and the QSA indexer keeps its no-grad KL target instead of redoing the teacher. The allocations a state formula misses

Four temporary-memory stories

These worked sizes follow the lab's token shape. They are separate examples, not four extra bars: concurrency, buffer reuse and fusion decide how many are live at once.

GDN: training is not inference

Token chunks carry matrix state

Decode carries one [48, 128, 128] FP32 state per layer. Chunked training materializes one state per 64-token chunk: ceil(T / 64) × 48 × 128 × 128 × 4 bytes. Splitting documents at 4K resets the recurrence but not the number of chunks. Full recompute makes this one layer's transient, not a saved tensor.

QSA: selection is data too

Indices and a teacher chunk

Each query reads 512 selected blocks of four keys plus up to three tail keys: [T, 2051] int64 indices. The KL teacher gathers those keys for 512 queries at a time and keeps only a [T, 512] FP32 target, which is cheaper to save than to recompute.

Dist-MoE: a planner, not autograd

Slots scale with the capacity factor

A layer must keep its input [T, D]. Saving everything for balanced routing adds x_gathered, h1 and the staged output: R × (D + 2F + D) × 2 bytes with R = 10T. The factor interpolates between the two; overflow is recomputed. Scratch is sized for the worst routed row count the run must tolerate.

Loss: a 248K vocabulary

Never hold the full logits

A full [T, 248320] logit tensor would rival a whole chunk's saved inputs. The chunked loss computes logits and their gradient one token chunk at a time, so only a slice is ever live. Its saved input is the final [T, 2560] hidden state.

BF16 reduction is a communication policy, not a master dtype. Reducing gradients in BF16 would shrink reduce-scatter payloads, but the master, optimizer-visible gradient and moments would stay FP32. It would not shrink the orange gradient bar.
Memory follows lifetime, not global batch

16 microbatches do not mean 16 saved forwards

A forward adds one saved set for its chunk; the matching backward releases it. With interleaving, a rank alternates between its two chunks, and its warmup decides how many forwards are unfinished at once. In PyTorch's interleaved 1F1B with PP2, VPP2 and 16 microbatches, rank 0 warms up with 4 forwards and peaks at 5 unfinished chunk forwards; rank 1 peaks at 3. 

Interleaved 1F1B warmup on rank r = (VPP - 1) * (M / rounds) + 2 * (PP - 1 - r),   rounds = floor(M / PP)
Peak unfinished chunk forwards    = warmup + 1   (when M is large enough)
Saved per chunk forward           = 12 * T * 10240 * 2  +  3 * T * 512 * 4   bytes
Dist-MoE slots                    = peak unfinished chunk forwards (one 12-layer slot each)

Interleaving halves the nominal bubble, from (PP − 1) / M to (PP − 1) / (M × VPP), but it does not halve activation memory: rank 0 holds five 12-layer chunk forwards instead of two 24-layer stage forwards, 60 layers of saved inputs instead of 48. And the stage boundary packet is the whole four-stream state: [16384, 10240] BF16, 320 MiB per microbatch per hop forward, with a matching gradient backward. VPP2 has three hops per microbatch instead of one.
